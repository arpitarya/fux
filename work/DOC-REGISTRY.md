# DOC-REGISTRY — the freshness tracker for **live** documents

**How to use this file.** One row per maintained doc: what triggers an update
to it, and when it was last verified true. **Bump the row in the same change
that touches the doc** — the row's date is the only thing that makes staleness
visible at a glance. A row older than ~30 days is a review prompt, not a
failure.

### The rule: this registry lists live documents only

**An archived document loses its row in the same change that archives it.**
Not struck through, not annotated "retired" — **deleted**, the same discipline
[`OPEN-WORK.md`](OPEN-WORK.md) applies to closed items, and for the same
reason: the file's length should mean something. A registry padded with
tombstones stops answering *"what do I have to keep true?"*, which is the only
question it exists to answer.

Three consequences, all mechanical:

1. **No row may point into [`../archive/`](../archive/README.md).** An archived
   doc is frozen and never updates, so a trigger and a last-verified date are
   meaningless on it. Where it went is the archive map's job, not this file's.
2. **Every row's target must exist.** A row for a deleted file is the same
   defect wearing different clothes.
3. **One row per document.** Two rows means two last-verified dates for one
   file, which is the confusion this file exists to prevent.

Enforced by [`../tests/test_doc_registry.py`](../tests/test_doc_registry.py).

**The archive map is deliberately not listed here.** It lives under `archive/`,
so rule 1 excludes it — and it does not need a row: the archive law in
`CLAUDE.md` and `tests/test_archive_law.py` already require it to exist and to
name a successor for everything in it.

**Contract:** every maintained doc has an update **trigger** and a
**last-verified** date. A task that fires a trigger updates the doc *and* its
row, in the same change. Docs large enough to carry §humans + §agents sections
update both.
