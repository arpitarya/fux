## ⚠ What SR-WORK-ENVIRONMENTS changed here, so a reader of the old document is not misled

| | before 2026-09-11 | now |
|---|---|---|
| **question** | *"is version B better than A?"* — paired quality rows and a p-value | *"how fast, and did the ranking change?"* Quality judgment is the **lab's**, always |
| **corpora** | `t100`/`t1000`/`t10000`, generated by importing `fux-lab/shared/generate/` | **its own** seven folders, its own generator, its own document shape |
| **answer key** | marker queries with known answers, graded pass/fail | **none.** A benchmark never says *"was it right?"* |
| **two versions** | one comparison among several possible run shapes | **every run, always** |

The `bench.py mcnemar` half of the old harness has no job here any more. It is
kept on disk as history and nothing calls it; a paired quality comparison is a
lab run against the golden ladder.

## Shape

```
~/my_programs/fux-benchmark/          # a git repo — the lab was lost once for not being one
  bin/
    gen_corpus.py     deterministic generator: seed + N -> one corpus folder
                      --keys writes the planted key into EXISTING tiers, in place
    queries.py        the fixed TIMING set, versioned, emitted with the corpus
    judged.py         the PLANTED KEY (W-150): 42 judged questions + 10
                      unanswerables, derived from gen_corpus's construction
                      rules alone — it reads no document and runs no fux
    bench.py          prepare | nullcontrol | latency | hits | answers |
                      rankdiff | report | file
    report.py         CAP-7: one self-contained theme-aware HTML page per run
    latency.py        the older interleaved timer, kept for the B5/B6 shapes
    bench_v1_mcnemar.py   the OLD harness (paired quality rows + a p-value).
                      SR-WORK-ENVIRONMENTS moved that question to the lab; nothing calls it, and
                      it is kept only so the 2026-08-28 filed run reproduces.
  corpora/
    docs-00100/ docs-00200/ docs-00500/ docs-01000/
    docs-02000/ docs-05000/ docs-10000/
      docs/           the generated documents
      queries.jsonl   the fixed TIMING set for this folder
      judged.jsonl    the judged questions + the planted unanswerables
      key.jsonl       the relevant document(s) per judged question
      MANIFEST.json   generator version, seed, per-file sha256, corpus sha256,
                      keyset version and the two key hashes
  arms/
    A/venv/           pip install 'fux-engine==<newest 1.x>'
    B/venv/           pip install -e ../fux    (the current build)
  runs/<date>/
    work/<arm>-<corpus>/    each arm's OWN copy of the corpus and its own .fux/
    rows/                   per-query rows, written as the run goes
```

⚠ **Each work directory is its own git repository.** `fux setup` anchors on the
**nearest git root**, not on `cwd` — the first attempt wrote `.fux/`, `.claude/`
and `.github/` into `fux-benchmark/` itself and left the corpus with no index.
Both arms do it, so it is not a version difference; it is a harness rule.

**`ARMS.toml` is generated into the RUN's evidence**
(`work/regression/<run>/evidence/ARMS.toml`), never kept at the harness root — a
manifest beside the harness describes whatever the harness is today, and a filed
number needs the manifest it was produced under. It names, per arm: install
source, resolved version, Python minor version, whether `.fux/enrich` is present,
and the corpus sha256 it read.

## The corpus

**Generated here, by `bin/gen_corpus.py`, and never imported from the lab.** The
lab's data is the sealed golden ladder; sharing a generator would make a timing
corpus and an evaluation corpus drift together, and would put the lab's material
where timing runs touch it.

- **Deterministic:** `gen_corpus.py --seed S --docs N` produces byte-identical
  output for the same arguments, on any machine. `MANIFEST.json` carries the
  generator version, the seed, every file's sha256 and a corpus sha256.
- **Document shape is SR-WORK-ENVIRONMENTS's** — about a thousand lines, lines up to about 300
  characters, carrying tables, charts, bullet points and Mermaid diagrams, in a
  mix of machine-made and several-author voices. The generator implements that
  sentence; the law is where it is stated.
- **Nested sets, not independent ones.** `docs-00200` contains every document in
  `docs-00100` plus 100 more, and so on up. A latency curve across the folders is
  then a curve in *corpus size* and nothing else — with independently seeded
  folders it would also be a curve in whatever the generator happened to emit.
- 🔴 **THE CORPUS CARRIES A PLANTED KEY since 2026-09-13** (W-150), and it cost
  no corpus byte. [SR-WORK-BENCHMARK](../../records/0053_WORK-benchmark.md)'s
  CAP-3 and CAP-4 need relevance judgments and well-formed unanswerables;
  `bin/judged.py` derives both from **the generator's own construction rules** —
  document `i` has domain `DOMAINS[i % 10]`, subject `SUBJECTS[(i // 10) % 20]`
  and a unique reference token — so it **reads no document and runs no fux.**
  - **`gen_corpus.py --keys` writes the key into the tiers that already exist**
    and asserts `corpus_sha256` did not move. **No corpus was regenerated**, so
    every timing filed before the key still compares.
  - **The unanswerables are absent by CONSTRUCTION**: a reference token past the
    pool's last document, a volume number past it, and a `<domain> <word>
    handbook` whose word is not in `gen_corpus.py`'s source at all — the
    generator can only write words it contains literally.
  - ⚠ **The TIMING set keeps no key and never will.** Its words are scattered
    randomly *inside* each document, so a key for it could only be built by
    re-reading the corpus, which is a key that agrees with whatever ranked it.
  - **Planted is not sealed.** Nothing from `work/golden/` enters this
    environment, and no Claude session reads the golden answer key.
- **Regenerating is a new corpus.** Timings taken against a different corpus
  sha256 are not comparable to the ones before it; say so in the report rather
  than plotting them together.

## The query set

- **Fixed, versioned, committed with the corpus** as `queries.jsonl`, and
  emitted by the same deterministic run that writes the documents.
- **No answer key, by design.** The benchmark asks *how fast* and *did the
  ranking change*; it never asks *was it right*. A key here would be a second,
  unsealed evaluation set competing with the lab's.
- **Every query must return something on both arms.** A query that returns an
  empty list times the refusal path, not the ranking path, and silently makes a
  version look fast. `bench.py prepare` fails the run if any query is empty on
  either arm.

## What every run produces

**Per run, per version, per corpus, per query:**

| artifact | what it holds |
|---|---|
| `evidence/latency.csv` | one row per query per arm per repeat: `run, arm, version, corpus, query_id, repeat, ms` — plus the warm-up rows, marked and excluded from statistics rather than dropped |
| `evidence/ranked-lists.jsonl` | one record per query per arm: `{run, arm, version, corpus, query_id, results: [{rank, path, score}]}` at a fixed `k` |
| `evidence/ARMS.toml` | the two arms as resolved |
| `RANKDIFF.md` | what moved against the **previous run of the same version** — queries whose top-`k` ordering changed, and by how much |

**Timing method, stated so a number can be read:**

- **3 warm-up repeats, then 10 measured**, per query per arm. Warm-up rows are
  written and marked, never silently discarded.
- **One query = one `fux ask --json` process**, cold-start included. That is what
  a consumer pays; timing an in-process call would measure a thing nobody runs.
- **Report the median and p95 per query**, and the median-of-medians per corpus.
  Never a mean — one scheduler hiccup owns it.
- **Ingest and build are timed separately** and are not part of a query number.

target.** 150 ms is 3× Python's measured p95 (50.2 ms at 10 000 documents), so

about a constant factor, and must never be reported as one.

## Standing rules

**0. Never delete it, never start a fourth harness.** Same rule as the lab, same
reason. New comparison work is a new `runs/<date>/` inside it.

🔴 **0a. ONE PROCESS PER `runs/<id>/`, and the harness enforces it now.**
Two sessions on this machine chose the run id `2026-09-12-l9` within three hours
on 2026-09-12. `bench.py latency` opens its row CSV with `"w"`, so the second
**silently truncated the first's 10 000-document pass mid-sweep** — and for the
overlap the two were **timing each other's CPU**, so numbers on both sides were
wrong in a way nothing asserts on. `summarise()` then printed a confident
three-query summary in the same format as a sixty-query one.

- **`bench.py` writes `runs/<id>/.owner`** with its pid and refuses a directory
  a live process holds, naming the pid.
- ⚠ **The null control could never have caught it.** It compares one arm to
  itself *inside one process*; the neighbour arrives from outside.
- **Row files are opened `"x"`, not `"w"`** — the lock stops the common case,
  exclusive-create stops the one the lock cannot see (a stale `.owner` cleared by
  hand). A guard whose own failure is silent is half a guard.
- 🔴 **Still unguarded, and it cost more than the collision did: a neighbour
  doing UNRELATED work on the same machine.** The same day, the other session
  was indexing golden-ladder rungs in `fux-lab` for two hours — no shared file,
  no shared run id, and **every latency measured in that window was inflated by
  an unknown amount.** The owner lock cannot see it; §Where it can and cannot run
  is the only mitigation and it is a sentence, not a check. **It was caught
  because a person said so afterwards**, which is not a mechanism.
- Filed: [`../regression/2026-09-12-benchmark-l9/`](../regression/2026-09-12-benchmark-l9/report.md)
  §The collision.

**1. The null control runs first, every time — and it is the same-corpus
repeat.** Arm A twice on the *same* corpus must give **identical ranked lists**
(latency will differ; ordering must not). A difference means the harness is
nondeterministic and **every number in that session is void**. Running this last,
after the interesting numbers exist, is how a broken harness gets believed.
⚠ **A cross-seed pairing is a rate check, not a determinism check** — query ids
are positional, so it compares different questions.

**2. Arms are interleaved, never sequenced.** `A B A B`, not `AAAA BBBB`.
Thermal drift on a laptop is a real effect, and sequencing hands the second arm a
different machine.

**3. Per-query rows are written as the run goes.** One row per query per arm,
under the run's own directory, before any aggregate is computed. An aggregate
reconstructed after the fact is not evidence.

**4. The harness never picks a threshold.** There is no pass/fail here at all —
the harness reports latency and what moved. A *decision* about a regression is a
record or a verdict, made by a person reading the filed numbers.

**5. It commits nothing to git — and its corpora are still KEPT.** Venvs and raw
timings are disposable; what survives into the repository is what lands in
[`../regression/<date>-<run>/`](../regression/README.md) under the per-run
contract.

🔴 **`corpora/_pool/` and `corpora/docs-*/` are NOT disposable.** Arpit,
2026-09-12: *"Do not delete the one thousand, two thousand, five thousand, and
ten thousand data setup. Keep it. We will keep on reusing the data."*

- **Gitignored is not scratch.** The **2026-08-20 `fux-lab` wipe** took W-78's
  corpora with their generator and those numbers can never be reproduced.
- **Regenerating is a new corpus** — §"Three things that are easy to get wrong"
  already says a timing against a different `corpus_sha256` may not be plotted
  with the ones before it. Wiping and rebuilding therefore **destroys every
  comparison**, not just the disk.
- A run that has to stop is stopped by killing the **run** and deleting its
  partial **rows** under `runs/<date>/rows/`. The corpus is never touched.

**6. Both arms, or no run.** A single-version run has nothing to say here and is
[SR-WORK-ENVIRONMENTS](../../records/0052_WORK-environments.md)'s veto 3. If the previous
major will not install, the run stops and files that as the finding.

## Where it can and cannot run

**Not on the Cowork device VM** — no network, Python 3.10; both arms install from
PyPI or a local editable install and need ≥ 3.11.

🔴 **Latency is machine-bound.** Every timing number in one run comes from one
machine in one session. A run that measures one arm in the cloud and the other on
a laptop has published two numbers that cannot be read together. Ranked lists are
deterministic and *are* comparable across machines — which is why they are the
half that survives a split session.

## The two-session blind protocol — retired here, 2026-09-12

**It no longer applies to this harness, and that is a consequence of SR-WORK-ENVIRONMENTS rather
than a relaxation.** The protocol existed because whoever wrote the corpus and
the query set and then read a *quality score* is `informed`, and no delta may be
stated from an informed run. This harness no longer produces a quality score:
its query set has **no answer key**, so there is no correctness anyone can fit,
and *"how fast"* and *"what moved"* are not contaminable by knowing the corpus.

🔴 **The protocol is not gone from the project — it moved to where the scoring
is.** Every evaluation run is a lab run under
[SR-RS](../../records/0133_predictions.md) decisions 11-15, which is where
`blind`/`informed` is declared. **A benchmark run still declares
`classification:`** like every filed run; it will read `informed` and that costs
nothing here.

## The hazards this harness has taught

- **A saturated query set looks exactly like two equal engines.** The 2026-08-28
  run came back 240/240 on both arms at every tier. Size a set for power *and*
  check the queries can express the effect.
- **`fux answer` writes its repeat-query `note:` to stderr**, so the harness
  captures stdout alone. Merging the streams makes `--json` unparseable
  intermittently, which reads as a flaky engine.
- **A generator bug corrupts both arms identically**, which looks like *"no
  detected change"* rather than like a bug. When both arms return the same
  surprising ranking, hand-read one generated document before believing it.

## Every run's evidence is filed

Per run, in the same change: create `work/regression/<date>-benchmark-<what>/`,
drop the report with `classification:` frontmatter and an `## Authorship`
section, write `ANALYSIS.md`, save `latency.csv`, `ranked-lists.jsonl` and
`ARMS.toml` under `evidence/`, and add a row to
[`../regression/README.md`](../regression/README.md).

**The reproduce command must actually reproduce.** A run whose numbers cannot be
regenerated is an anecdote.
