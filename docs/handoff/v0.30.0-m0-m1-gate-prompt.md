You are executing the first milestone of the Fux v0.30 rebuild. The full
spec is `docs/handoff/v0.30.0-m0-m1-gate-handoff.md` — **read it first and
treat its Definition of Done, Scope, and Non-negotiables as binding.** This

The single most important thing about this task: **phase 3 is an experiment
that is allowed to fail, and a failure is a successful outcome.** You are
not trying to make pruning look good. You are measuring whether it works,
against a threshold that was written down before the numbers existed.

## Task, in four phases — do them in this order

**Phase 0 — check the ground.** `git status`. If the reset (archived
`src/`, new docs) is uncommitted, commit it as its own commit first, so
your work is separable in history. Then verify the archived engine runs:
`cd archive/v0.26 && uv run pytest -q`. If it doesn't, fix by *invocation*
(paths, working dir, venv) — never by editing archived source. If you
can't, stop and tell me.

**Phase 1 — doc hygiene (W-03).** Make the repo's docs true:
`GLOSSARY.md` (v0.30 vocabulary), `INTERVIEW.md` (a reset entry for the
next model), `DOC-REGISTRY.md` (clear the two ⚠ rows). For **CLAUDE.md**:
prepare the rewrite as a **diff for my review — do not apply it silently.**
It steers every future session; I read it before it lands.

**Phase 2 — ADR-0016, the naming decision (W-02).** If I've answered the
naming question, write it as accepted. If I haven't, write it as
`status: proposed` recommending `enriched`, and keep going — do not block.

**Phase 3 — THE GATE (W-04).** Build, in a new `tools/pruning-eval/`:
- the KL top-k term selector as a **pure, stdlib-only, tested function**
  (handoff §5.2 — it gets ported into the engine later, so write it as
  production code, not a script);
- the harness (handoff §5.3), which runs both arms through **one scorer**,
  varying **only the index**.

The correctness point you must not get wrong: **recompute df, n, and field
lengths from the pruned postings.** That is the system we would actually
ship. Borrowing the baseline's statistics to make scores line up would
measure a system that doesn't exist. Also produce the diagnostic arm
(pruned postings + baseline df) so losses can be attributed.

Report per corpus × per k ∈ {baseline, 128, 64}: hit@5, P@10, MRR, a
rare-term slice, a failure catalogue (every lost top-5 hit, with a cause),
the fraction of documents actually pruned, and total kept postings.

**Phase 4 — the verdict (W-05).** Write `docs/adr/0017-pruning-eval-gate.md`
with the numbers and the ship/kill call against the **pre-registered**
threshold in handoff §5.4. File the evidence under
`docs/conformance/<date>-pruning-eval/` (README + ANALYSIS + raw outputs +
the exact reproduce command).

**Phase 5 — scaffold (W-01) — ONLY if phase 4 says PASS.** Then, and only
then, create `src/fux/`, `pyproject.toml` at `0.30.0.dev0`, a fresh
CHANGELOG, and update `.github/` paths. If phase 4 says FAIL or lands
ambiguous: **stop, and say so plainly.** Do not scaffold. Do not soften the
result. A recorded negative that saves months is the best possible outcome
of this task.

## Required workflow

1. **Explore before writing.** The archived engine's index build and query
   path are not what you'd guess; read them.
2. **Plan and pause.** After exploring, lay out the harness design and the
   files you'll create, and wait for my confirmation before implementing
   phase 3.
3. **Implement incrementally.** Develop the harness against the small
   fixture and acme/orbit corpora; run the 100k arm once, last.
4. **Update docs in the same change** — `WORKLOG.md` (an entry per
   substantive exchange), `OPEN-WORK.md` (W-item statuses and the P1 row),
   `DOC-REGISTRY.md` rows for anything you touched, and the
   `ingest-mode-naming` compare doc's status. Don't report done while the
   docs contradict the repo.
5. **Verify:** the selector's unit tests, the harness's identical-arm and
   no-op-pruning sanity checks, and a re-run producing byte-identical
   numbers. Report done only when these pass.

## Constraints (hard)

- **Stdlib only** in the selector and anything portable. No numpy, pandas,
  or scipy anywhere — not even in the harness, not even for convenience.
- **Deterministic:** no wall-clock, no unseeded randomness, no reliance on
  set iteration order. Same corpus → byte-identical report.
- **Do not modify `archive/v0.26/`.** Wrap, subclass, or monkeypatch from
  the harness. If that's genuinely impossible, stop and ask.
- **Do not modify** `docs/archive/`, `docs/paper/`, or any compare doc's
  verdict except `ingest-mode-naming`.
- **Do not build any of M2–M6** — no MST keyspace, no BIC, no segments, no
  kernel, no adapters, no cache, no hooks. However well phase 3 goes.
- **Never move the threshold after seeing the numbers.** If the result is
  ambiguous, write it up as ambiguous and hand it to me.
- CLAUDE.md changes are **proposed, never applied**.

## Tests

Selector: known distributions → expected ranking; tie-break determinism;
k > vocabulary; empty document; a universal term scores ≈ 0; collection
model built from the unpruned corpus. Harness: identical-arm byte equality;
k=∞ ≡ baseline. Run with `uv run pytest tools/pruning-eval/tests -q`.

## Guardrails

- **Ask before:** editing anything under `archive/`, changing the
  pre-registered threshold or the metrics definition, adding any
  dependency, or scaffolding after a non-PASS result.
- If a requirement here conflicts with what you find in the code, **stop
  and ask** — do not reconcile it silently.
- If the numbers land between "clearly passes" and "clearly fails," that is
  my call, not yours. Write it up and hand it over.

## Models

Phases 0–3 and 5: **Sonnet** — tightly specified, mechanical.
Phase 4 (analysis + ADR-0017): **Opus**, especially if any corpus lands
within a point of the threshold. Reading a failure catalogue and calling
kill-or-ship is the judgment work where a cheaper model rationalizes a
marginal result into a pass. If in doubt, hand the raw outputs to a fresh
Opus session and let it write the verdict cold.
