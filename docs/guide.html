Fux

A search index for your documents that lives in your git repo — as text you can read, diff and review. No server, no vector database, no API key, and no second copy of your content.

01What Fux is

One sentence: rank from a small committed index, fetch content from the systems that own it, and verify at answer time.

Your documents stay put

The repo, a wiki, a web page. Fux never copies them and never stores their text — it stores statistics that make them findable.

The index is committed

.fux/index/ — 256 shards of canonical JSON, one line per document. Small enough for git, plain enough to diff and merge.

Answers quote the original

The index says which document answers you. The words come back from that document as it stands today, with a freshness verdict attached.

Why "index", not "database". What Fux commits is an index: statistics that make documents findable. It is load-bearing vocabulary, not a style preference — the moment it reads as a database, people expect it to hold the content, and holding content is the one thing it must never do.

02How to use it

Install and set up

pip install fux-engine          # or: uv add fux-engine
fux setup                       # writes the files YOU own — never rewritten after
fux ingest && fux build          # build the index, then the fast path

fux setup writes fux.toml, the source lists under .fux/sources/, the fetcher templates, and your agent files. Everything it writes is yours: commit it, edit it, Fux will not overwrite it.

Tell it what to index

fux add docs/                   # a directory, walked recursively
fux add README.md               # a single file
fux add https://wiki.corp/page  # a URL — recorded AND fetched
fux remove docs/legacy/
fux update                      # re-read everything listed, re-fetching URLs

Ask

CommandGives youReach for it when
fux ask "…" --jsonRanked results with score, loc, archivedYou want candidates and will judge them
fux find "…"Bare pathsYou are piping into something else
fux answer "…"One cited answer, re-scored on the source's current bytesYou want the answer, with a freshness verdict
fux explain <loc>Edges into and out of one document You are asking what something depends on
fux graph "…"The neighbourhood around the best answers You are orienting in unfamiliar territory
fux path <a> <b>How two documents connect You suspect a relationship and want the chain
fux doctorInstall health, index health, URL health Something is off and you want it named

Line ranges come from answer, never from ask

The single most confusing thing about the surface, so it goes first. ask and find return documents. Only answer returns a span with line numbers. If you ran fux ask and expected :L12-L40, nothing is broken — it is the wrong verb for that question.
VerbGranularityloc looks likeNetwork
fux askdocumentdocs/mesh.md none — index only
fux finddocumentdocs/mesh.md none — index only
fux answerspan docs/mesh.md:L10-L13 fetches each cited source
This is L4, not an omission. A line range can only be computed by chunking the fetched bytes — the index holds statistics, not text, so it has nothing to count lines in. Giving ask line numbers would mean making it fetch, and ask is one of the verbs that is offline by default. The split is the law showing through the surface.

What a citation actually is

So: fux answer does not hand you a document and wish you luck. It cites a span — a heading-delimited passage with a line range and the sha of the bytes it read.

$ fux answer "why did we choose helix"

# Service mesh

We adopted a service mesh to stop a slow dependency taking down checkout.

## Why we chose Helix

Helix gave us per-route timeouts and circuit breaking without touching
application code. The alternative was a library in every service.

  -- docs/mesh.md:L1-L8 (sha 516bef067812, current)

The same thing in --json, which is what an agent should read:

"citation": {
  "id":        "file:docs/mesh.md",
  "loc":       "docs/mesh.md:L10-L13",
  "sha":       "516bef06781262a0a64b10027316c18d668eeccb",
  "freshness": "current"
}
Verbatim from a real run, not illustrated. Examples that are typed rather than captured rot silently, and this project has paid for that once already.

How the spans are chosen

StepRuleWhy
SplitOn markdown headings A document's headings are the author's own segmentation. It costs nothing, needs no model, and produces boundaries a human already agreed with.
MergeSections under 120 bytes fold into the next one A two-line passage is a citation nobody can read in isolation.
Split againSections over 4 000 bytes split on paragraph boundaries One 40 KB section would otherwise eat the whole byte budget by itself.
Addresspath:L<start>-L<end>, 1-based and inclusive An agent acts on a citation by opening a file at a line. An ordinal would force a second call just to find out which lines those are.

Text before the first heading is its own passage. A preamble is content, and dropping it silently is how the one sentence that answers the question disappears.

The passages are transient, and that is L2, not a design preference. They exist for the length of one query — never written to .fux/, never cached to disk, never put in the index. They are also what makes the byte budget honest: because chunking runs on the fetched bytes, the assembler knows every candidate's real size instead of estimating it from index statistics. A web-scale system has to guess here; this one does not.
An ordinal is kept beside the line range, and the reason is worth knowing: line numbers move when a document reflows, and a stored citation would then point somewhere else without ever looking wrong. The ordinal survives that.

Read the freshness verdict

fux answer fetches each cited source and compares it against what was indexed. Four states, and the fourth exists precisely so the other three stay honest:

VerdictMeansWhat to do
currentThe source still matches the indexCite it plainly
staleThe source changed since ingest The quoted passage is from the current bytes — the answer is right, the index is behind. Say so.
unverifiedThe source could not be reached Do not present it as confirmed
cachedServed from a TTL cache We looked recently — which is not we looked just now
Why cached is never folded into current. Collapsing we did not look into we looked and it was fine is the failure the whole refer plane exists to prevent. A knob that lies about freshness is worse than no knob.

03Running it as an agent

fux setup writes agent instructions for Claude, Kiro and Copilot. The most important thing they carry is how to find the command.

The defect this closes was live and silent. fux is a console script, so it is on PATH only where its installing environment's bin/ is. In any repo whose Fux lives in an unactivated .venv/, an agent got command not found, concluded not installed, and silently fell back to grep — while the engine sat there and the committed index sat beside it. It did not error. It degraded, and the degradation read exactly like an honest answer.

The invocation ladder

fux --version                 # a venv is active, or fux is global (pipx, uv tool)
uv run fux --version          # a uv-managed repo
./.venv/bin/fux --version     # venv present, not active   (Windows: .venv\Scripts\fux.exe)
python -m fux.cli --version   # importable, no script installed

Probe with --version and cache the winner for the session. Never which — it answers is there a file, not does it run, and a stale shim from a deleted venv passes it.

Never activate, never install. An agent calls the absolute path from rung 3. It does not source an activate script, modify PATH, or install anything — mutating the user's shell so a read-only query can run is a side effect nobody consented to, and in a non-interactive subshell it usually does not even persist. This is enforced by a test, because it is exactly the fix a well-meaning edit reaches for.

If every rung fails, the agent says which ones it tried and that it fell back — never that the package is absent. That one sentence turns a silent degradation into a diagnosable failure.

Two Kiro traps worth knowing. Kiro CLI does not support steering inclusion modes, so every file in .kiro/steering/ enters every interaction there — which is why the usage guidance ships as a skill. And Kiro custom agents load neither skills nor steering by default: they need explicit skill:// / file:// entries in resources. Fux cannot write someone's agent config, so the skill says it.

04Architecture

Two planes. One is committed and holds statistics; one is derived, gitignored, and holds speed. Deleting the derived plane costs you time, never an answer.

The loop that closes the gap

The refer plane already fetched every cited URL and already computed whether its sha still matched the index — then threw the fact away. So a URL that changed upstream kept its old terms, stopped ranking into the candidate window, was never cited again, and nothing ever noticed. It now records that document in the dirty list, where a narrowed re-ingest corrects the terms.

This buys recall, not correctness. A changed document could never be mis-answered — the verdict beside every citation is what stops that. It could only fail to surface. That is a weaker good than correctness, and the work is priced as buying the weaker one.

Why concurrency is safe here

Sequential fetching was never what made the index deterministic — the trailing sort is. fetch_all sorts its results before returning, so completion order never reaches a committed byte. That single fact is what makes a thread pool cheap to reason about.

A blanket pool would have been silently wrong. The shipped cdp.py holds one WebSocket in a module global that every fetch reuses; two threads writing frames onto it produce plausible documents attributed to the wrong URLs. That lands in the committed index, passes every determinism check, and is caught only by a human reading an answer. Hence MAX_PARALLEL: declared by the fetcher, never detected by Fux, and 1 when absent.

05The seven laws

These are not guidelines. Every record cites them by number and none restates them.

L1$0, stdlib-only runtime. No third-party runtime dependency. The frontmatter parser and every codec are hand-rolled on purpose.
L2Content is never durable outside its source system. The index holds statistics, never content. The whole architecture rests on this.
L3Deterministic — no model in the maintenance path. Same sources produce a byte-identical index. Nothing calls a model to build one.
L4Offline by default. Network access only inside explicit, fenced, opt-in paths — fux add <URL> and fux update.
L5Hashed meta is the default for non-git sources, enforced at write time. It closes an ACL-mismatch leak.
L6Say "index", not "db". Load-bearing vocabulary.
L7Python ≥ 3.11.

06Decisions made

Fux keeps 41 architecture decision records. Every behaviour change updates its record in the same commit — enforced by a test in CI and a commit-msg hook, not by trust.

The four calls of 2026-08-26

QuestionCallConsequence
Answer-time fetchingEvery cited URL is fetched before the final answer Already shipped — and it withdrew two proposed flags outright
How a changed URL is detectedQuery-driven dirty list, unconditional Prioritisation comes out usage-weighted for free
Parallel fetchingDeclared capability, min(declared, configured) Safe for the thread-unsafe browser fetcher by construction
A local content storeNot built Copying the corpus blunts the wedge for two narrow wins
The withdrawal worth understanding. A proposal for update --warm and answer --memo was folded in and then withdrawn by the first call above. If the bytes are fetched regardless, a warmed store saves nothing on the answer path, and an answer memo caches the output of a pure function whose inputs were just downloaded. What survived is a report: answer now says whether anything changed since you last asked the same question. Nothing is stored, nothing is replayed.

Some decisions that shaped the engine

DecisionWhy
The pruned index is dead, not deferred A pre-registered gate closed FAIL. The committed index carries full postings, permanently.
The dense lane and its model were deleted Measured 0 fixed / 2 broken at every setting that fires — the model mean-pooled static vectors, so the lane was as order-blind as BM25F. The wheel was 97% model.
A cross-encoder reranker was refused onnxruntime is not byte-identical across architectures, which would break clone it and run the query.
The post-commit hook defers An inline re-index cost 44s on a 20-document commit, because cost tracks corpus size, not delta size. The hook writes a dirty list and spawns a detached runner.
Randomness was removed, not seeded A fixed seed does not survive a Python version that reorders a set. A test asserts the absence of the import, by parsing the AST.
max_age_seconds was refused There was no recorded ingest time, so the bound could not have been honoured. Freshness is content verification instead — which answers the question exactly rather than approximately.

Record status

Of 41 records, 26 are accepted and 15 remain proposed. Proposed does not mean unbuilt — several describe shipped behaviour and are waiting on ratification, which is a human step and is owed.

07Decisions pending

Twenty-seven open forks. Every one is a judgement about what counts as success, and a metric chosen badly is wrong quietly for months — so none is an agent's to pick.

AreaOpenThe one that bites first
URL freshness8 forks (1 ruled) Whether the fetcher contract gains an optional validate() — gated on a measurement that needs a real URL corpus
What "right" means6 forks Whether the answered gate is measured at all. It needs a judge model — ruling "measure it" without pinning the model and the prompt makes every future comparison meaningless.
The records themselves6 rulings + 2 A record whose premise died and now stands unargued — the one state a record should never be in
Measurement discipline1 scope defect An informed run "never supplies a delta" — which as written forbids reporting a file size
The agent surface4 forks (1 ruled) Whether python -m fux becomes a second permanent entry point
A time-sensitive one. The narrowed-refresh flag has no name yet — --dirty, --stale, --changed. It is free to choose today and a deprecation cycle once anything ships against it. The same is true of the tunables file's key names: they are a shipped interface now, and the record still being proposed is the only thing making a rename free.
Why the measurements are blocked on corpora, not on code. Two of the six planned phases did not land, and neither is a coding task: one needs a real URL corpus to run fux update twice against, the other needs the graded playground repo. Producing a number for either without its corpus is precisely the failure the measurement discipline exists to prevent.

08What is not verified

The end-to-end suite has not been seen green. It spawns the real CLI in a subprocess and fails identically on a clean tree in the environment this release was built in — identical before and after, so the change introduces no regression. That is not the same claim as passing. It needs one run on a real Python 3.11+ install before release.

The unit suite is 1 433 green. It ran under a harness-only shim that backports one stdlib module, because the build environment had only Python 3.10 — so it tested 3.10, not the supported floor. The shim never enters the repo.

Why this section exists at all. Two runs in this project's history passed their number and failed their claim, and a human caught both — not the metric. Stating what a measurement did not establish is cheaper than discovering it later, and a project that hides its unverified edges teaches everyone to distrust the verified ones.
