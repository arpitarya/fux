# ADR-MCP: the MCP server

- **Name:** `ADR-MCP` — cite this everywhere; never cite the number
- **Status:** proposed
- **Date:** 2026-08-23
- **Feature:** the agent-facing interface — W-76 Phase 5
- **Owns:** `src/fux/mcp.py`
- **Laws:** L1 (stdlib-only) — **held, not bracketed**; L2, L4 unchanged

## 1 · Examples

```console
$ fux mcp                      # stdio; a host spawns this, a human rarely does
```

A host's first three messages, and what comes back:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}
-> {"protocolVersion":"2024-11-05","capabilities":{"tools":{}},
    "serverInfo":{"name":"fux","version":"1.0.0"}}

{"jsonrpc":"2.0","method":"notifications/initialized"}
-> (nothing — a notification has no id and MUST NOT be answered)

{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"fux_search","arguments":{"query":"retry payments","k":1}}}
-> {"results":[{"path":"docs/retry-policy.md",
                "title":"Retry policy for the payments service",
                "score":3.706,"sha":"f9421e0910df...","archived":false,
                "superseded":false}],
    "ranked_by":"accelerator"}
```

Verbatim from a run against the fixture repo on 2026-08-23.

> **Amended 2026-08-26 (W-84) — every result row now also carries
> `"headings"`,** the document's committed headings that match the query, best
> first, at most three. The capture above predates it and is annotated rather
> than rewritten. Read each row as gaining, e.g.,
> `"headings":["Retry and backoff"]` — or `"headings":[]`, which is a real
> answer and not an omission.
>
> **This is not a retreat from decision 4**, and the distinction is the whole
> point: a heading is **not a span**. There is no fetch, no chunking and no
> line arithmetic — `phrases` was committed at ingest and the record is already
> in hand for its `sha`, so the cost is a set intersection. What it buys is the
> decision an agent makes *before* it spends a `fux_passage` call: not only
> which document, but where in it. Decision 9 records it.

## 2 · Context

The consumer is an agent in a coding session, and an agent calls a retrieval
tool many times per task. Two facts set the design:

- **Process start-up dominates.** A CLI spawn costs ~50–150 ms of Python
  start-up *before any ranking happens*, against a warm p95 of 27 ms at 8 870
  documents and 64 ms at 10 000. The interpreter is more expensive than the
  work.
- **An agent acts on a citation by opening a file at a line.** W-76 Phase 5
  made `path:L12-L40` the citation format for that reason; this record is the
  other half of the same phase.

### Decision

**1. stdio JSON-RPC, hand-rolled, no dependency.** MCP over stdio is
newline-delimited JSON-RPC 2.0 — `json` and `sys.stdin`. Adopting the `mcp`
package (and `pydantic` behind it) to read a line and dump a dict would break
**L1 for convenience**, on the surface most exposed to churn. **L1 is held
here, not bracketed.**

**2. Three tools, not nine verbs.** `fux_search`, `fux_passage`,
`fux_related`. The CLI's shape is for humans exploring; the tool surface is
for an agent with a task. `explain` and `path` fold into `fux_related`,
because an agent asking *"what else was decided with this?"* does not care
which of the three verbs answers it.

**3. `answer` is NOT exposed.** The agent **is** the answerer. Handing it a
pre-composed answer throws away the reason it called a retrieval tool, and
invites it to relay prose it did not verify. `fux answer` remains on the CLI,
for humans.

**4. `fux_search` is document-level, deliberately.** Doc 06 of the ideal set
sketched line ranges on the search result itself. That would mean fetching and
chunking **every hit on every search** — turning the cheap call into the
expensive one — so spans stay with `fux_passage`, which is the call the agent
was going to make anyway. The index knows documents; the refer plane knows
spans.

> **Amended 2026-08-26 (W-84) — the tool DESCRIPTION contradicted this
> decision, in the one place an agent reads without a human in the loop.**
>
> `fux_search`'s `description` said it *"returns ranked results with
> **line-range citations** and content hashes"*. `_search` has never returned a
> line range and, by this decision, never will. So the surface that teaches an
> agent how to use fux taught it to look for a field that is not there — and,
> reading no range, to conclude fux cannot do spans at all, when `fux_passage`
> is the tool that does.
>
> ⚠ **This is the same defect commit `ad95a24` fixed in `docs/guide.html` and
> the usage skills earlier the same day, surviving in the machine-facing
> copy** — which is worse, because a human notices a doc that disagrees with
> the output in front of them and an agent does not. The description now says
> *"ranked documents with content hashes and the headings that match your
> query — section-level, not line-level; call `fux_passage` for the lines"*,
> and `test_search_does_not_claim_line_ranges_it_never_returns` pins both
> halves: the string, and the fact that no result `path` carries a `:L` span.
>
> **The lesson is the one W-84 inherited from `ad95a24`:** every gate in this
> repo checks that documentation is TRUE; none checks that it is COMPLETE, and
> none at all watched the tool descriptions, which are documentation compiled
> into the binary.

**5. Every result carries the `sha` the ranking used.** An agent that reads a
file and gets a different hash knows the index is behind **without having to
trust it**. That is the whole premise of ranking from an index and fetching
from the owner, made checkable at the tool boundary.

**6. A tool failure is a result with `isError`, never a JSON-RPC error.** The
agent should see a tool that answered *"no"* — something it can act on — not a
transport fault, which it usually cannot. A JSON-RPC error is reserved for an
actual protocol fault: an unknown method, an unknown tool, unparseable input.

**7. `fux_passage` refuses to escape the repository.** `resolve()` collapses
`..` **before** the containment check, so a traversal cannot slip through by
being spelled differently.

**8. A notification is never answered.** `notifications/initialized` arrives on
every connection and carries no `id`. Replying is a protocol error that some
hosts treat as fatal.

**9. Every result carries the matching `headings`, always present** (W-84,
2026-08-26). The document's committed `phrases` filtered to the ones the query
asked about — best first, at most three, `[]` when none match or the record is
`hashed` (which carries no display text at all, L5).

- **It is free here.** `_search` already reads the whole record for its `sha`,
  and `phrases` was extracted at ingest. The added cost is a set intersection
  per hit.
- **`[]` is a real answer.** An absent key is a trap, not a signal: a host
  cannot distinguish *"no heading matched"* from *"this server predates the
  field"*.
- **It is the same selection `fux ask` renders**, from the same function —
  `query/headings.py::headings_for`, owned by [ADR-ASK](0004_ask.md)
  decision 10, which carries the argument for why heading level and not line
  level. Two implementations of one rule is where the CLI and the MCP payload
  drift apart, and consequence 3 below already names that risk.

## 3 · Consequences

- **`fux mcp` is a verb, not a flag.** It is a long-running server, not a
  query. [ADR-CLI](0002_cli-surface.md) gains a fifth group rather than
  overloading the read verbs, and veto 1 (no subcommand trees) is unaffected.
- **The server holds the index open across calls.** That is the point, and it
  means a rebuilt accelerator mid-session is not picked up until restart.
  Acceptable while `is_fresh` is cheap; revisit if a host keeps servers alive
  for days.
- **`--json` on the CLI and the MCP payload are now two surfaces** that can
  drift. They are generated from the same `AskResult`, so drift requires
  someone to add a field to one on purpose.
- **W-84 is the first field added to both on purpose, 2026-08-26**, and the
  clause above is exactly why it was added through one shared function rather
  than two renderers. `headings` comes from `query/headings.py::headings_for`
  on both sides; the payloads still differ in shape (`path` vs `loc`, a rounded
  score vs a full float) because they always have, and this record does not
  change that.
- **The tool descriptions are documentation that no gate reads.** W-84 found
  `fux_search` claiming line-range citations it has never returned — the same
  wrong claim `ad95a24` had just fixed in the human docs. `TOOLS` is prose
  compiled into the package, and `tests/test_mcp.py` now asserts one sentence
  of it. That is a spot check, not a gate: nothing checks the other two
  descriptions against what their handlers do.

## 4 · Alternatives considered

- **A Python library API (doc 06 option B).** Real, and it is what the CLI and
  this server both already sit on. Rejected as the *primary* interface for the
  same reason doc 06 gave: no agent host imports a Python module, they all
  speak MCP. The library layer is what makes a future port thin.
- **The `mcp` package.** Rejected under decision 1.
- **Exposing all nine verbs.** Rejected under decision 2. A tool list is
  prompt context on every single request; nine entries of it, most never
  called, is a tax on every task the agent performs.

## 6 · Veto condition

**Reopen this decision if** a major agent host drops MCP for a different tool
protocol — the library layer under this file is what makes that a thin port.

**Veto 1: a dependency appears in `src/fux/mcp.py`.** L1 is held here.

```bash
grep -nE '^(import|from) ' src/fux/mcp.py
# expect: json, sys, pathlib, and fux's own modules. Nothing else.
```

**Veto 2: `fux_answer` appears in the tool list.** Decision 3.

**Veto 3: a notification draws a reply**, or a tool failure is returned as a
JSON-RPC error rather than `isError`. Both are protocol faults that a host may
treat as fatal.

```bash
pytest -q tests/test_mcp.py
```
